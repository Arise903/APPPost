## 零、怎么用

<!-- GUIDE -->

> 本工作台把检查进度、权限配置、备注证据和发布批次保存在你的私有项目中。

### 开始检查

- 阅读本页并确认后，按顺序完成清单；不适用的项目可以跳过，并在备注中说明原因。
- 勾选先保存在当前浏览器草稿中，点击「保存」才同步到云端。
- 备注与证据、权限配置和发布信息分别保存；网络失败时请查看错误提示。
- 项目设置可隐藏账号系统和未成年人相关的不适用条目。

### 发布与协作

- 发布前填写版本、构建号和负责人，保存进度后归档本次发布。
- 返回项目工作台可导出完整 JSON，或由所有者邀请编辑者和查看者。
- 多个成员同时保存会校验版本，冲突时先导出草稿，再刷新核对。
- 恢复备份会一起恢复清单、权限配置、备注和发布信息；恢复前保留当前快照。
- 证据字段只保存路径或链接，不会自动上传你的本机文件。
- 每次发布后清空检查进度可开始新一轮；此前的归档记录会继续保留。

## 一、配置项清单

### 1. Adjust（广告归因）— `AdjustManager`

- [ ] `appToken` 已替换为**正式环境真实 Token**，且 iOS / Android 使用各自平台的 Token（不是同一个值）
- [ ] `config.isAdServicesEnabled` 的取值已**按业务定位最终确认**（当前为 `false`）
- [ ] 已确认 `false` 时的行为符合预期：
  - Adjust SDK **完全不初始化**，ATT **不发起请求**（避免无意义的隐私弹窗 + 空跑链路）
  - 调试期通过编译期常量 / `--dart-define` 区分，不要把开关硬编码在业务代码里
- [ ] 已配置 Adjust 深度链接 / 场景值（deeplink、归因回调）

> ⚠️ `isAdServicesEnabled = false` 却仍保留 ATT 流程 = 白白弹权限、拖慢启动、给审核留下"声明了却没用"的疑点。开关必须真的短路整条链路。
>
> 💡 ATT 的声明统一在「权限与隐私配置」面板的「跨应用追踪」里勾选，清单里不单独配。

### 2. 自有统计 — `AnalysisApi`

- [ ] `_baseUrl` 已指向**生产环境**域名
- [ ] `projectId` 已配置，且与环境（prod / staging）对应正确
- [ ] Release 构建不会指向测试环境（建议用 `--dart-define` 注入，检查打包脚本）
- [ ] UUID 读取 / 生成逻辑已验证：首次启动生成、卸载重装是否重置（策略需明确写死）
- [ ] 用户上报、token 上报、行为队列（离线缓存 + 上报）三条路径均可用
- [ ] token 无效 / 过期时的降级逻辑已验证（不影响主流程）

### 3. 用户反馈 — `feedbackApiKey`

- [ ] `feedbackApiKey` 已替换为正式 Key（未使用测试 Key / 空值）
- [ ] 反馈入口在设置页可达，路径不深（≤ 2 次点击）
- [ ] 反馈提交链路**真机自测通过**（能收到反馈、能失败重试）
- [ ] 反馈渠道（邮箱 / 表单）真实可用，有人处理

### 4. 订阅商品与环境

#### 4.1 环境切换（最容易出事的环节）

- [ ] **沙盒 / 本地测试环境已完全关闭**，Release 包不会连到 StoreKit 测试环境
  - Xcode → Target → Build Phases → 确认没有 `Copy StoreKit Configuration File` 步骤留在 Release
  - 或直接扫代码：`grep -ri "storetest\|localconfiguration\|SKTestSession" lib/ ios/ android/`
- [ ] Android 侧 `BillingClient` 的测试开关（`setTestAPI` / `isBillingTest` 之类）在 Release 里为 false
- [ ] 订阅数据源指向**生产商品**，不是沙盒商品
  - 运行时日志里能拉到真实商品 ID，而非 `com.apple.test.*` 这类沙盒商品
- [ ] 自有服务器的订阅状态接口也指向生产库，测试环境的订单没有写进生产
- [ ] 环境开关由编译期常量 / `--dart-define` 控制，不在业务代码里硬编码 `kDebugMode`
- [ ] **已用 Release 包真机真实购买过一次**（TestFlight 能买 ≠ App Store 能买）

> ⚠️ **最高频事故**：Release 包里还留着 StoreKit 测试配置。表现是「测试阶段一切正常，上架后买不了」——
> 线上用户拿到沙盒商品 ID，或审核员在沙盒环境实测失败。提审前必须在 Release 包上完成一次真实购买。

#### 4.2 商品、周期与价格

- [ ] 订阅商品 ID 已在 App Store Connect / Google Play Console 创建并**通过审核**（未过审的商品线上不可售）
- [ ] 商品 ID 与代码里的映射一致（iOS 与 Android 各自的 product id）
- [ ] 订阅周期已配置并与产品设计一致（周 / 月 / 年 / 自定义周期）
- [ ] 每个周期都有独立价格点（Price Point）
- [ ] 价格点已设置**销售范围（Base Territory）**—— 不设销售范围 = 全球商店里买不到
- [ ] 各档位的权益差异与代码逻辑一一对应（升级 / 降级策略已实现）
- [ ] 显示价格按地区本地化后符合预期（不是看自己填的数值）
- [ ] **免费试用**已配置：试用时长（3 天 / 7 天）、试用结束后的价格正确回落到订阅价
- [ ] 试用是否可重复领取、是否与优惠叠加，行为与预期一致
- [ ] **优惠 / 促销价**已配置：
  - [ ] 优惠价金额
  - [ ] 优惠生效时间（起止日期，注意时区与时区切换）
  - [ ] 参与优惠的商品（哪些订阅档位）
  - [ ] 每个用户可享受次数（单次优惠 / 续订优惠可重复）
  - [ ] 优惠与免费试用的叠加规则
- [ ] 家庭共享（Family Sharing）按产品策略开启或关闭
- [ ] 订阅分组（Subscription Group）正确，同组内商品可互相升级
- [ ] 涨价通知流程已验证（App Store 要求提前通知，代码里也要处理续订时的价格变更）

#### 4.3 购买流程验证

- [ ] 购买成功、取消、恢复购买、续订失败全部走通
- [ ] 沙盒账号（Sandbox Tester）已覆盖上述路径
- [ ] 恢复购买能正确还原订阅状态（换机 / 重装后）
- [ ] 订阅状态**不阻塞**统计初始化（见第二节）
- [ ] 订阅状态变化能正确上报自有统计（用户 / token / 行为队列）

### 5. 发布账号与证书

#### 5.1 Apple 开发者账号

- [ ] 当前用的是**正式上架账号**，不是个人测试账号或临时账号
- [ ] 账号主体（个人 / 公司）与 App Store 显示的名称一致
- [ ] **中途换过账号的话**，bundle ID 必须用新账号重新注册
  - 换账号后沿用旧 bundle ID = 无法提交，这是硬性限制
- [ ] 旧账号下的 App 已按需处理（转移或删除），不影响新账号提交
- [ ] 协议（Apple Developer Program License）已签署且生效
- [ ] 税务信息、银行信息已提交（影响 Apple 抽成结算）
- [ ] 账号下所有用到的 bundle ID 都已注册
- [ ] App Store Connect 里的 App 已创建，元信息（名称、描述、关键词、分类）已填

#### 5.2 证书与描述文件

- [ ] **发布证书（Distribution Certificate）**已创建，有效期未过期
- [ ] **描述文件（Provisioning Profile）类型为 App Store / Distribution**，不是 Development
  - 类型选错 = 能装到设备但传不上架
- [ ] 描述文件包含所有实际用到的能力：
  - [ ] Push Notifications（用了推送就必须有）
  - [ ] Associated Domains（用了 Universal Links / App Links 必须有）
  - [ ] App Groups（用了共享数据必须有）
  - [ ] Merchant ID（内购必须）
- [ ] App ID 的 Capabilities 与代码实际用到的功能**一致**，多余的已删除（审核会质疑）
- [ ] APNs 推送的 p8 密钥或证书已配置（代码里调了推送就必须有，否则推送静默失败）
- [ ] Xcode 的 Team 选对了，且与 App Store Connect 记录的证书是同一套
  - 上传构建用的证书与后台记录的不一致 → 报签名不匹配
- [ ] 上传构建用的证书和后台 App Store Connect 记录的证书是同一个（否则上传报签名不匹配）

#### 5.3 Android 侧账号与签名

- [ ] Google Play 开发者账号已通过身份验证（一次性注册费用）
- [ ] 已启用 Play App Signing，上传密钥（upload key）**已备份**
- [ ] release 签名密钥（jks）**已备份**，且与 Play 记录一致（丢了就无法再上传）
- [ ] 密钥库密码 / 别名 / 密码有妥善记录（团队协作需要）
- [ ] 目标 API Level 符合 Google Play 最新要求
- [ ] 内测 / 封闭测试轨道的测试账号已准备（审核员会用到）

## 二、初始化流程核对

### 目标时序

```text
App 启动
  ↓
初始化 Flutter
  ↓
初始化 AnalysisApi：读取/生成 UUID，加载用户、token、行为队列状态
  ↓
完成订阅基础配置 → runApp()
  ↓
首帧渲染完成 → 独立启动统计流程
  ↓
并行执行两条链路：
  ├─ Adjust 链路（阻塞等待 ATT）
  │    等待 App 前台 + 界面就绪
  │      ↓
  │    检查并按需请求 ATT
  │      ↓
  │    等待明确结果：允许 / 拒绝 / 受限
  │      ↓
  │    关联 UUID → 初始化 Adjust（只执行一次）
  │
  └─ 自有统计链路（不等待 ATT、不等待 Adjust）
       尝试获取 AttributionToken（最多等待 3 秒）
         ↓
       上报用户
         ├─ 有有效 token：随用户一起提交
         └─ 无 token：先上报用户，后续单独补传
```

### 逐条验收

- [ ] `runApp()` 在订阅基础配置完成后调用，**首帧渲染完成**才启动统计流程
- [ ] Adjust 链路**必须等 ATT 明确结束**才能初始化 Adjust
- [ ] ATT 未决定 / 请求失败 → 继续等待并重试，**不阻塞**启动，也不擅自初始化 Adjust
- [ ] Adjust 初始化有**幂等保护**，无论重试多少次只执行一次
- [ ] ATT 结果为「允许 / 拒绝 / 受限」三种之一时都能正常推进，不卡死在某一种分支
- [ ] 自有统计链路**不等 ATT、不等 Adjust 初始化**，与 Adjust 链路真正并行
- [ ] AttributionToken 获取最多等 3 秒，超时后走「无 token」分支，不无限挂起
- [ ] 无 token 时：用户先上报，token 后续单独补传（不丢数据）
- [ ] 上报失败后按前台 **5 → 15 → 60 秒**间隔有限重试
- [ ] 进入后台时**暂停重试**，回到前台可继续（定时器生命周期正确）
- [ ] 订阅初始化与商品加载**独立进行**，不阻塞统计链路

## 五、权限与隐私配置

> **本章涵盖所有需要权限声明与隐私说明的内容**，原先散在配置项清单、审核要点里的
> 权限与隐私条目都已归并到这里。
>
> 实际配置片段由「权限配置」面板生成到文末附录，本章负责**核对一致性**：
> 面板勾了什么 → 政策怎么写 → 问卷怎么选 → 代码怎么调，四处必须对得上。

### 5.1 隐私政策内容与披露

- [ ] 隐私政策线上地址可访问（**必须 HTTPS**，非内网 / 本地地址）
- [ ] 「关于我们」地址可访问
- [ ] App **内**有隐私政策入口（不能只在官网，审核员会在 App 内查找）
- [ ] 隐私政策内容覆盖：
  - [ ] 收集的个人信息清单（设备标识符、用户 ID、订阅状态、崩溃日志等）
  - [ ] **第三方 SDK 清单**（必须与实际集成的 SDK 完全一致，含 Adjust）
  - [ ] 数据用途、存储地点、保留期限
  - [ ] 用户数据删除 / 账号注销的**具体操作路径** <!-- if:hasAccountSystem -->
  - [ ] 儿童隐私条款（COPPA / 儿童个人信息网络保护规定） <!-- if:targetMinors -->
  - [ ] 联系方式（邮箱 + 响应时效承诺）
- [ ] 隐私政策覆盖**每一项**实际采集的数据类型（对照附录的隐私问卷勾选结果）
- [ ] 隐私政策写明**每项权限的用途**，与 Info.plist 的 `UsageDescription` 文案一致
- [ ] 隐私政策内容与**实际采集行为一致**（App 内采集但政策没写 = 拒；政策写了但没采 = 可疑）
- [ ] 隐私政策中已说明「用户主动提交的内容将被收集用于改进产品」（反馈功能）

### 5.2 平台隐私声明与表单

- [ ] App Store Connect「App 隐私」问卷已填，且与隐私政策内容一致
- [ ] Google Play Console「数据安全」表单已填，且与实际采集一致
- [ ] 隐私问卷与政策内容已按「权限配置」面板生成的清单逐项核对（面板勾了什么，问卷就该选什么）
- [ ] iOS **PrivacyInfo.xcprivacy** 已随包提交（App Store Connect 后台可上传）
- [ ] PrivacyInfo.xcprivacy 中声明的 Required Reason API 与代码实际调用一致
- [ ] 隐私清单里声明的数据类型与 App 隐私问卷**没有矛盾**

### 5.3 用户同意与撤回

- [ ] 首次启动的隐私同意弹窗已实现（Apple 要求：追踪前必须先取得同意）
- [ ] 同意弹窗提供「同意 / 不同意」两个**同等显著**的选项
- [ ] 不同意时 App 仍可使用核心功能（不得强制同意才能用）
- [ ] App 内提供**撤回同意**的入口（设置页可重新调整权限与追踪开关）
- [ ] 隐私政策有 App 内入口（设置页），不只是外部网页
- [ ] 撤回同意后，追踪 SDK 立即停止上报

### 5.4 账号注销与数据主体权利

- [ ] 账号注销入口可达（iOS **强制要求**，隐藏会被拒） <!-- if:hasAccountSystem -->
- [ ] 注销流程在 App 内可完整走完，不依赖客服 <!-- if:hasAccountSystem -->
- [ ] 注销后数据被真实删除或匿名化 <!-- if:hasAccountSystem -->
- [ ] 若有第三方 SDK，注销时同步通知其删除数据 <!-- if:hasAccountSystem -->

### 5.5 iOS 权限声明

> 本节**不单独配置**权限。声明文案由「权限配置」面板生成，
> 这里只核对「面板生成的」与「代码实际调用的」是否一致。

- [ ] 面板生成的 `*UsageDescription` 已全部写入 Info.plist，且**文案具体说明用途**
- [ ] 面板勾选的权限与代码里**实际调用**的 API 一一对应（不多不少）
- [ ] 权限弹窗只在用户主动触发相关功能时申请，**不得启动即弹**
- [ ] 用户拒绝权限后，App 仍有合理降级路径（不能崩溃、不能卡死）
- [ ] 面板里没有勾但代码里用到的权限（如 PhotoKit 保存、蓝牙、ATT），已补勾并重新生成

### 5.6 Android 权限申请

- [ ] 面板生成的 `<uses-permission>` 已全部写入 `AndroidManifest.xml`
- [ ] 面板勾选的权限与代码实际调用**完全一致**（不多不少）
- [ ] 危险权限在运行时动态申请，而非仅在 Manifest 声明
- [ ] Android 13+ 用 `READ_MEDIA_IMAGES` 而非旧的 `READ_EXTERNAL_STORAGE`
- [ ] Android 12+ 蓝牙用 `BLUETOOTH_CONNECT` / `BLUETOOTH_SCAN`
- [ ] Android 13+ 通知用 `POST_NOTIFICATIONS` 并运行时申请
- [ ] 后台位置权限（`ACCESS_BACKGROUND_LOCATION`）已单独申请页面，且确有业务必要
- [ ] 权限被拒绝后提供「去设置」引导

### 5.7 权限与隐私的一致性核对

> 这一节是**提交前最后一遍对账**：面板、隐私政策、平台问卷、代码，四个来源必须指向同一件事。

- [ ] 面板生成的隐私政策段落已合并进实际政策页面（不是只留在附录里）
- [ ] 隐私政策里写的权限用途与代码里弹的权限弹窗文案**一致**
- [ ] Google Play 的权限用途说明与 App 内弹窗文案**一致**
- [ ] 权限用途说明齐全（相机、麦克风、通知等），不只是一句笼统的「需要权限」
- [ ] 未申请的后台权限已在 Manifest 中移除（避免无谓的审核质疑）
- [ ] 敏感权限（健康 / 通讯录）没有作为核心功能的强制前置条件
- [ ] ATT 声明与实际调用一致（面板勾了「跨应用追踪」就必须在代码里弹 ATT；反之没勾就不能调 ATT API）
- [ ] 广告归因用到的设备 ID 权限与实际使用一致（面板勾了「跨应用追踪」才声明）
